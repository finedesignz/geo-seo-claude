<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cron process -> geo-api HTTP | cron sends a Bearer token + audit-target URLs across the network to OUR api |
| CRON_TARGET_URLS (operator env) -> cron | operator-supplied list of audit targets; untrusted strings |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Information Disclosure | cron logging (cron.ts/main.ts) | mitigate | Log only url + job_id/status; NEVER the Authorization header or CRON_API_TOKEN (mirrors auth.ts discipline). Asserted indirectly: tests never read logs but the code path logs url/jobId only. |
| T-07-02 | Tampering | CRON_TARGET_URLS parsing (env.ts) | mitigate | Validate each entry with `new URL()` before any POST (fail-fast); the api re-validates+normalizes with zod and the worker's safe fetcher classifies IPs. The cron itself NEVER fetches the target URLs — it only POSTs them to OUR api, so no SSRF surface is added in the cron process. |
| T-07-03 | Elevation of Privilege | cron bearer token (CRON_API_TOKEN) | accept | Dedicated low-privilege `cron` consumer_id (D-4); a compromised token can only enqueue audits, rotated via Coolify env. No code mitigation needed in this plan. |
| T-07-04 | Denial of Service | partial-failure loop (cron.ts) | mitigate | try/catch per URL, continue on failure; one bad URL cannot abort the batch (Pitfall 3). |
</threat_model>
